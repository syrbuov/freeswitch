# Технический отчёт по mod_amqp

Проанализирована рабочая копия FreeSWITCH с HEAD
`1ff547f988186de7f1903eba16d5477cde72e27d`.

Отчёт подготовлен по результатам статического анализа исходников. Запуск
FreeSWITCH, проверки с RabbitMQ и воспроизведение гонок не выполнялись.
Исходники и конфигурация не изменялись. Ссылки ниже относительны каталогу модуля;
номера строк относятся к проанализированной версии.

Сейчас `event_filter` управляет подписками ядра FreeSWITCH по типу события и
подклассу. Универсального сопоставления заголовков в модуле нет. Его можно
реализовать внутри producer-профиля перед сериализацией, используя существующие
структуры событий и функции чтения заголовков. Изменения ядра FreeSWITCH для
этого не требуются.

## 1. Парсинг event_filter и регистрация bindings

### 1.1. Значения по умолчанию

Парсер находится в [`mod_amqp_producer_create()`](mod_amqp_producer.c#L163).
До чтения параметров профиль получает одну подписку:

```c
profile->events[0].id = SWITCH_EVENT_ALL;
profile->events[0].subclass = SWITCH_EVENT_SUBCLASS_ANY;
profile->event_subscriptions = 1;
```

`SWITCH_EVENT_SUBCLASS_ANY` определён как `NULL`, а не строка `"*"`:
[`src/include/switch_event.h:128`](../../../include/switch_event.h#L128).

### 1.2. Разбор значения

В [ветке `event_filter`](mod_amqp_producer.c#L265) выполняются следующие действия:

1. Значение копируется в memory pool профиля.
2. `switch_separate_string()` разбивает его по запятым в массив
   `argv[SWITCH_EVENT_ALL]`.
3. Каждый элемент разделяется по первому `^`: слева остаётся имя события,
   справа — подкласс.
4. `switch_name_event()` преобразует имя в `switch_event_types_t`.
5. Тип и указатель на подкласс сохраняются в `profile->events[]`.

Примеры поддерживаемого синтаксиса:

```xml
<param name="event_filter" value="CHANNEL_CREATE,CHANNEL_DESTROY"/>
<param name="event_filter" value="CUSTOM^sofia::register"/>
<param name="event_filter" value="SWITCH_EVENT_ALL"/>
```

Особенности разбора:

- `switch_name_event()` сопоставляет имена без учёта регистра; поддерживает
  короткую форму и форму `SWITCH_EVENT_…`. Технически ветка с префиксом сравнивает
  строку начиная с позиции 13, не проверяя сам префикс.
- Общий разделитель обрабатывает кавычки, экранирование и удаляет окружающие
  обычные пробелы. Это поведение `switch_separate_string()`, а не отдельная
  грамматика модуля.
- Отсутствующий `event_filter` означает подписку на все события.
- Пустая строка даёт ноль подписок.
- Несколько параметров `event_filter` последовательно перезаписывают счётчик и
  элементы массива; они не объединяются как независимые группы.
- Условия по произвольным заголовкам, отрицания, AND/OR и регулярные выражения
  в этом парсере отсутствуют.

Источники:
[`switch_name_event()` — src/switch_event.c:438](../../../switch_event.c#L438),
[`cleanup_separated_string()` — src/switch_utils.c:2687](../../../switch_utils.c#L2687),
[`switch_separate_string()` — src/switch_utils.c:2855](../../../switch_utils.c#L2855).

### 1.3. Регистрация и сопоставление

После создания очереди и запуска producer-потока модуль вызывает
`switch_event_bind_removable()` для каждого элемента. В callback передаётся
указатель на профиль через `user_data`, а возвращаемый binding сохраняется
в `event_nodes[i]`. См. [mod_amqp_producer.c:352](mod_amqp_producer.c#L352).

На стороне ядра:

- [`switch_event_bind_removable()`](../../../switch_event.c#L2060) создаёт
  отдельный узел подписки. Дедупликации по имени `"AMQP"`, callback или
  `user_data` нет.
- [`switch_events_match()`](../../../switch_event.c#L233) проверяет `event_id`
  и `event->subclass_name`.
- Обычный подкласс сравнивается через `strcmp()`, с учётом регистра.
- Подкласс `NULL` допускает события с любым подклассом и без него.
- Строка `*` отдельного значения «любой подкласс» здесь не имеет.
- Ядро содержит специальные ветки `file:` и `func:`. Их поведение не следует
  смешивать с будущим универсальным сопоставлением заголовков.

Таким образом, нынешний `event_filter` фильтрует по внутренним полям события;
он не сравнивает строковые заголовки `Event-Name` и `Event-Subclass`
непосредственно.

## 2. Producer profiles и их жизненный цикл

### 2.1. Структуры

Основные структуры определены в [`mod_amqp.h`](mod_amqp.h#L65).

| Структура | Назначение |
| --- | --- |
| `mod_amqp_producer_profile_t` | Параметры публикации, подписки, очередь, поток, соединения, состояние остановки и memory pool |
| `mod_amqp_events_t` | Тип события и подкласс одной подписки |
| `mod_amqp_keypart_t` | Заголовки или литералы для одной части routing key, включая fallback |
| `mod_amqp_message_t` | Готовый JSON и routing key; исходное событие не хранится |
| `mod_amqp_connection_t` | Параметры брокера, AMQP state и ссылка на следующее соединение |
| `mod_amqp_globals_t` | Общий pool модуля и отдельные hash-таблицы producer, command и logging profiles |

У каждого producer-профиля собственные memory pool, ограниченная очередь и
поток отправки. Общего publisher-потока для всех профилей нет.

Подписки представлены полями `event_subscriptions`, `events[]` и
`event_nodes[]`. Размер обоих массивов — `SWITCH_EVENT_ALL`. В структуре также
есть отдельный указатель `eventNode`, который рассмотренный путь регистрации
не использует.

### 2.2. Значения по умолчанию

Источник: [`mod_amqp_producer_create()`](mod_amqp_producer.c#L163).

| Параметр | Значение |
| --- | --- |
| Подписка | `ALL`, любой подкласс |
| Exchange | `TAP.Events` |
| Тип exchange | `topic` |
| Размер очереди | 5000 сообщений |
| Переподключение | 1000 мс |
| Circuit breaker | 10000 мс |
| Content type | `text/json` |
| Delivery mode | `-1`: свойство AMQP не устанавливается |
| Delivery timestamp | Включён |

### 2.3. Создание

Последовательность создания:

```text
memory pool → профиль и параметры → список соединений
→ очередь → producer-поток → event bindings → producer_hash
```

Соединение с RabbitMQ открывается асинхронно в потоке. Успешный
`mod_amqp_producer_create()` означает создание локальных ресурсов и подписок,
но не подтверждает доступность брокера.

Профиль становится доступен callback сразу после регистрации первого binding —
до завершения регистрации остальных и до вставки в hash.

Параметры соединений создаются через
[`mod_amqp_connection_create()`](mod_amqp_connection.c#L195) и принадлежат pool
профиля. Соединения образуют список `conn_root`; `conn_active` указывает на
текущее активное соединение.

### 2.4. Уничтожение

[`mod_amqp_producer_destroy()`](mod_amqp_producer.c#L115) выполняет:

1. Удаление профиля из hash по имени.
2. Установку `running = 0`.
3. `switch_thread_join()` producer-потока.
4. Закрытие всех соединений.
5. Извлечение и уничтожение оставшихся сообщений очереди.
6. Уничтожение memory pool.
7. Обнуление переданного указателя.

**Сам destructor не снимает event bindings.** В штатных reload и shutdown это
делает вызывающий код глобально. При ошибке частичного создания такого
предварительного снятия нет.

## 3. Путь события: callback → serialization → queue → RabbitMQ

### 3.1. Доставка callback

[`switch_event_deliver()`](../../../switch_event.c#L400) последовательно
обходит подписки конкретного типа события и подписки `ALL`. Перед каждым
callback ядро устанавливает:

```c
(*event)->bind_user_data = node->user_data;
```

Весь обход и выполнение callback происходят под read lock общего `RWLOCK`.
Разные события могут обрабатываться параллельно.

Далее [`mod_amqp_producer_event_handler()`](mod_amqp_producer.c#L71):

1. Получает профиль из `evt->bind_user_data`.
2. Проверяет наличие профиля и `profile->running`.
3. Проверяет срок circuit breaker.
4. Выделяет `mod_amqp_message_t`.
5. Вызывает `switch_event_serialize_json()`.
6. Строит routing key.
7. Вызывает `switch_queue_trypush()`.

Проверок заголовков между получением профиля и сериализацией сейчас нет.

### 3.2. Сериализация

[`switch_event_serialize_json_obj()`](../../../switch_event.c#L1818) и
[`switch_event_serialize_json()`](../../../switch_event.c#L1856) преобразуют
все заголовки события в JSON:

- обычные значения становятся строками;
- заголовки с массивом значений становятся JSON-массивами;
- при наличии body добавляются `_body` и `Content-Length`.

Модуль не проверяет результат сериализации. Callback не передаёт
`switch_event_t` в очередь: сообщение содержит самостоятельный JSON. Это
соответствует жизненному циклу ядра, которое уничтожает событие после
завершения доставки всем подписчикам.

### 3.3. Routing key

[`mod_amqp_producer_routing_key()`](mod_amqp_producer.c#L41) использует
`format_fields`:

- части соединяются точками;
- поле с `#` в начале трактуется как литерал;
- остальные поля читаются через `switch_event_get_header()`;
- при включённом fallback заголовки перебираются до первого существующего
  значения;
- значения кодируются через
  [`amqp_util_encode()`](mod_amqp_utils.c#L211).

Максимальное число частей — `MAX_ROUTING_KEY_FORMAT_FIELDS`, равное 10;
число fallback-вариантов на часть ограничено
`MAX_ROUTING_KEY_FORMAT_FALLBACK_FIELDS`, равным 5. Буфер routing key имеет
размер `MAX_AMQP_ROUTING_KEY_LENGTH`, равный 255.

Это формирование адреса публикации, отдельное от отбора событий.

### 3.4. Очередь и circuit breaker

При успешном `trypush` сообщение забирает sender-поток. При ошибке callback:

- устанавливает `circuit_breaker_reset_time`;
- уничтожает текущее сообщение;
- последующие события отбрасывает до истечения интервала.

Проверка breaker выполняется до сериализации, однако при его срабатывании
callback всё равно пишет ошибку в лог для каждого отклонённого события.
Комментарий об ограничении повторяющихся ошибок не полностью соответствует
реализации.

Очередь синхронизирована собственным mutex: см.
[`switch_apr_queue_trypush()`](../../../switch_apr_queue.c#L196).
Обёртка модуля ядра —
[`switch_queue_trypush()`](../../../switch_apr.c#L1279).
FIFO описывает порядок постановки сообщений; при параллельных callback это
не гарантирует порядок возникновения событий.

### 3.5. Sender-поток и публикация

[`mod_amqp_producer_thread()`](mod_amqp_producer.c#L442):

- открывает соединение при отсутствии активного;
- объявляет exchange;
- получает сообщение через `switch_queue_pop_timeout()` с ожиданием до одной
  секунды;
- вызывает `mod_amqp_producer_send()`;
- уничтожает сообщение после успешной отправки;
- сохраняет текущее сообщение при ошибке для повторной попытки после
  восстановления соединения.

Пока сохранённое сообщение не отправлено, следующие сообщения не извлекаются.
При выходе из потока текущее сообщение уничтожается.

[`mod_amqp_producer_send()`](mod_amqp_producer.c#L382) вызывает
`amqp_basic_publish()` на канале `1`, передавая exchange, routing key и JSON
body. Свойства включают content type, опциональные delivery mode и timestamp.
При отрицательном результате соединение закрывается и `conn_active`
сбрасывается.

Произвольные FreeSWITCH-заголовки находятся в JSON body. Они автоматически не
становятся AMQP headers. Поэтому добавление фильтрации FreeSWITCH-заголовков
не требует изменения AMQP properties.

Publisher confirms и обработка подтверждений в producer отсутствуют;
`mandatory` и `immediate` передаются как `0`. Успех `amqp_basic_publish()`
здесь не является подтверждением попадания сообщения в очередь потребителя.

## 4. Конфигурация, reload и освобождение ресурсов

### 4.1. Загрузка

[`mod_amqp_load()`](mod_amqp.c#L57):

- инициализирует глобальное состояние и три hash-таблицы;
- вызывает `mod_amqp_do_config(SWITCH_FALSE)`;
- регистрирует API-команду `amqp`;
- подключает logging callback.

[`mod_amqp_do_config()`](mod_amqp_utils.c#L90) получает конфигурацию через
`switch_xml_open_cfg("amqp.conf", ...)`, затем читает секции `<producers>`,
`<commands>` и `<logging>`.

Актуальный пример структуры —
[`conf/vanilla/autoload_configs/amqp.conf.xml`](../../../../conf/vanilla/autoload_configs/amqp.conf.xml#L1).
[`README`](README#L45) описывает старую схему `<settings>` и старые имена
параметров, поэтому использовать его как точную спецификацию текущего парсера
нельзя.

### 4.2. Reload

API callback [`amqp_reload()`](mod_amqp.c#L47) без анализа аргументов вызывает
`mod_amqp_do_config(SWITCH_TRUE)`.

Reload устроен следующим образом:

1. Сначала открывается XML. Если открыть его не удалось, старые профили
   сохраняются.
2. Вызывается
   `switch_event_unbind_callback(mod_amqp_producer_event_handler)` для всех
   producer-подписок модуля.
3. Уничтожаются producer и command profiles.
4. Отключается logging callback и уничтожаются logging profiles.
5. Все профили создаются заново из XML.
6. XML освобождается.

Существенные последствия:

- **Reload не транзакционный:** после начала удаления старой конфигурации
  отката нет.
- Ошибка создания отдельного профиля только логируется; итоговый
  `mod_amqp_do_config()` всё равно возвращает `SWITCH_STATUS_SUCCESS`.
- В период отсутствия bindings события не поступают в producer.
- Остаток очередей уничтожается, а не отправляется до конца.
- Перезапускаются также command и logging profiles.
- Logging callback отключается при reload, но обратного
  `switch_log_bind_logger()` в этом пути нет. Он регистрируется только при
  первоначальной загрузке модуля.

`amqp` сам не вызывает `switch_xml_reload()`.
[`switch_xml_open_cfg()`](../../../switch_xml.c#L2499) получает конфигурацию
через XML-подсистему, включая подключённые providers и текущий XML root:
[`switch_xml_locate()`](../../../switch_xml.c#L1757). Поэтому для файловой
конфигурации нельзя считать `amqp` заменой `reloadxml`. Обработчика
`SWITCH_EVENT_RELOADXML` в `mod_amqp` также нет.

### 4.3. Shutdown и гарантии снятия подписок

Штатный [`mod_amqp_shutdown()`](mod_amqp.c#L87) снимает producer bindings,
уничтожает профили, отключает logger и уничтожает hash-таблицы.

Снятие bindings обеспечивает ожидание выполняющихся callback:
[`switch_event_unbind_callback()`](../../../switch_event.c#L2134) берёт
write lock того `RWLOCK`, который удерживается при доставке событий. Это
защищает последовательный штатный teardown, но не компенсирует отсутствие
unbind внутри producer destructor.

Закрытие AMQP ресурсов выполняют
[`mod_amqp_connection_close()`](mod_amqp_connection.c#L41) и
[`mod_amqp_connection_destroy()`](mod_amqp_connection.c#L271). JSON и
оболочка сообщения освобождаются через
[`mod_amqp_util_msg_destroy()`](mod_amqp_utils.c#L236).

Если реализация будет вынесена в отдельный `.c`, потребуется обновить
[`Makefile.am`](Makefile.am#L7) и
[`mod_amqp.2017.vcxproj`](mod_amqp.2017.vcxproj#L136).

`mod_amqp_message_t` и AMQP transport менять для самой фильтрации не требуется:
решение о пропуске события принимается до создания сообщения. Эта структура
используется также logging-профилями, что дополнительно ограничивает полезность
помещения туда producer-specific правил.

### 5.2. Существующие средства ядра

- `evt->event_id` и `switch_event_name()` — для канонического типа.
- `evt->subclass_name` — для внутреннего подкласса.
- [`switch_event_get_header()` / `switch_event_get_header_idx()` / `switch_event_get_header_ptr()`](../../../switch_event.c#L825)
  — для произвольных заголовков.
- [`switch_event_header_t`](../../../include/switch_event.h#L65) — для доступа
  к массиву значений.
- [`switch_event_unbind()`](../../../switch_event.c#L2175) — для снятия
  конкретного binding.

Менять `switch_event_t`, event binding API и сериализацию ядра ради
модульной фильтрации не требуется.

### 5.3. Организация правил и подписок

Рекомендуемая организация: неизменяемые правила в pool профиля, проверяемые
callback только на чтение. Подписки ядра должны охватывать события, необходимые
всем правилам, но доставлять одно событие одному профилю один раз.

Возможны два варианта:

- Один binding `ALL` на профиль: простая семантика без пересечений, но callback
  вызывается для всех событий.
- По одному binding на нужный конкретный тип; если требуется `ALL`,
  использовать только его. Подклассы и заголовки проверять в callback.

Перед реализацией необходимо явно определить:

- AND/OR между условиями и правилами;
- поведение при отсутствии заголовка и при пустом значении;
- регистр значений;
- обработку массивов и повторяющихся заголовков;
- поддерживаемые операции сравнения;
- источник истины для `Event-Name` и `Event-Subclass`: внутренние поля либо
  строковые заголовки;
- поведение при ошибочном правиле.

Имена заголовков существующий getter сравнивает без учёта регистра. Для
значений такого общего правила нет. Нельзя автоматически переносить
регистронезависимость имени события на значения произвольных заголовков.

При обычном создании события ядро добавляет `Event-Name` из `event_id`, а
`Event-Subclass` — из подкласса. Это реализовано в
[`switch_event_prep_for_delivery_detailed()`](../../../switch_event.c#L1972)
и [`switch_event_create_subclass_detailed()`](../../../switch_event.c#L747).
Однако сами поля структуры и список заголовков — разные представления данных,
что важно учитывать при определении семантики универсального фильтра.

## 6. Ограничения, гонки, дубли и совместимость

### 6.1. Ошибочное имя может расширить подписку

При неудаче `switch_name_event()` парсер только пишет CRIT и продолжает работу.
Слот не исключается из `event_subscriptions`:

- первый слот сохраняет предварительно установленный `ALL`;
- следующие изначально обнулённые слоты содержат ID `0`, то есть
  `SWITCH_EVENT_CUSTOM`;
- при повторных параметрах возможно сохранение ранее записанных значений.

Обнуление выделенной структуры подтверждается
[`switch_core_perform_alloc()`](../../../switch_core_memory.c#L518), а
`CUSTOM` — первый элемент
[`switch_event_types_t`](../../../include/switch_types.h#L2082).
Это поведение следует непосредственно из кода, хотя отдельный сценарий
в работающем FreeSWITCH не воспроизводился.

### 6.2. Пересечения подписок дают повторные публикации

Примеры:

```text
ALL,CHANNEL_CREATE
CUSTOM,CUSTOM^sofia::register
CHANNEL_CREATE,CHANNEL_CREATE
```

В каждом случае соответствующее событие вызывает callback больше одного раза
в одном профиле. Каждое выполнение отдельно сериализует событие и ставит
сообщение в очередь. Несколько профилей также независимо публикуют совпадающие
события.

Основание: отдельная регистрация каждого элемента в
[`mod_amqp_producer_create()`](mod_amqp_producer.c#L352), отсутствие
дедупликации в `switch_event_bind_removable()` и обход всех подходящих узлов
в `switch_event_deliver()`.

### 6.3. Частичное создание и владение bindings

После успешной регистрации части подписок последующая ошибка приводит к
`mod_amqp_producer_destroy()`. Он уничтожает pool, но bindings сохраняют
`user_data = profile`. Последующая доставка создаёт риск use-after-free.
При новом механизме правил исправление этого пути необходимо до усложнения
регистрации.

Глобальный и индивидуальный unbind нельзя механически совместить. Нынешний
глобальный unbind освобождает узлы, но не обнуляет `profile->event_nodes[]`.
Если после него добавить обход этих указателей в destructor, возникнет
обращение к освобождённым bindings. Требуется единая модель владения.

Источники: [регистрация и `err:`](mod_amqp_producer.c#L352),
[destructor](mod_amqp_producer.c#L115),
[глобальный unbind](../../../switch_event.c#L2134).

### 6.4. Повторяющиеся имена профилей

Повторяющиеся имена не проверяются. `switch_core_hash_insert()` использует
замену существующей записи:
[`switch_hashtable_insert_destructor()`](../../../switch_hashtable.c#L194)
удаляет старый элемент hash. При этом старый producer-профиль не уничтожается.
Его поток и подписки могут продолжить работу вне учёта `producer_hash`;
обычный обход при shutdown его уже не найдёт.

Соответствующая обёртка —
[`switch_core_hash_insert_destructor()`](../../../switch_core_hash.c#L144);
профиль вставляется в hash в [mod_amqp_producer.c:366](mod_amqp_producer.c#L366).

### 6.5. Параллельный reload

В `mod_amqp_globals_t` отсутствует mutex для конфигурационных операций.
Параллельные вызовы API могут одновременно снимать подписки, обходить и
изменять hash, уничтожать и создавать профили. Блокировки ядра защищают список
event bindings, но не всю последовательность reload.

При последовательном штатном reload предварительный глобальный unbind
ожидает завершения callback. Поэтому риск освобождения профиля во время
callback нельзя приписывать любому reload без учёта этой защиты.

### 6.6. Разделяемые поля

`running` читается sender-потоком и записывается управляющим потоком;
`circuit_breaker_reset_time` читают и изменяют параллельные callback.
В модуле нет atomic или mutex для этих обращений. Возможны гонки состояния
breaker и повторяющиеся логи. Потокобезопасность очереди эти поля не защищает.

Источники: [`mod_amqp_producer_profile_t`](mod_amqp.h#L95),
[callback](mod_amqp_producer.c#L71),
[destructor](mod_amqp_producer.c#L115),
[sender-поток](mod_amqp_producer.c#L442).

### 6.7. Лимиты и стоимость callback

Массивы `events`, `event_nodes` и временный `argv` имеют размер
`SWITCH_EVENT_ALL`. Диагностики превышения лимита списка нет. Этот предел нельзя
переносить на число произвольных условий.

Сериализация и будущая фильтрация выполняются под общим read lock событий:
дорогие regex или большое количество линейных поисков увеличат нагрузку и
время ожидания unbind. Регулярные выражения, если они появятся, следует
подготавливать при загрузке профиля; правила не должны изменяться callback.

### 6.8. Гарантии доставки и остановка

Потери возможны при заполнении очереди, breaker, reload, остановке и отсутствии
подходящей RabbitMQ-маршрутизации. Повторная отправка сохранённого сообщения
после сетевой ошибки может дать дубль, если брокер уже принял предыдущую
попытку. Текущий код не обеспечивает ни exactly-once, ни гарантированную
at-least-once доставку.

Остановка не имеет строгого общего таймаута. Перед освобождением соединений
destructor ждёт sender-поток. Ожидание очереди ограничено секундой, но
подключение, AMQP RPC и сетевые операции выполняются синхронно без общего
дедлайна остановки в коде модуля.

### 6.9. Сопутствующие ограничения транспорта

Эти места не реализуют фильтрацию, но влияют на поведение producer и на
безопасность использования заголовков:

- В `mod_amqp_producer_thread()` для объявления exchange используется локальное
  `durable = 1`, хотя `exchange-durable` парсится в профиль.
- После ошибки объявления exchange активное соединение сразу не сбрасывается;
  следующая итерация может перейти к публикации.
- Перебор резервных соединений в `mod_amqp_connection_open()` выполняется при
  ошибке открытия socket. Ошибка login/channel не переводит текущую попытку на
  следующий broker.
- В timestamp properties заполняются два AMQP header, но `num_entries`
  установлен в `1`.
- Буфер routing key не инициализируется после `switch_malloc()`. При
  отсутствующем значении возможен `strlen()` неинициализированной области;
  `amqp_util_encode()` не принимает ёмкость буфера, а `strncpy()` не гарантирует
  завершающий ноль. Использование длинных произвольных заголовков в routing key
  требует отдельного исправления этих мест.

Источники: [объявление exchange](mod_amqp_producer.c#L442),
[перебор соединений](mod_amqp_connection.c#L118),
[AMQP properties](mod_amqp_producer.c#L404),
[routing key](mod_amqp_producer.c#L41),
[кодирование](mod_amqp_utils.c#L211).

### 6.10. Обратная совместимость

Будущая реализация должна сохранять либо явно документировать изменение
следующих особенностей:

- короткие и префиксные имена событий;
- синтаксис `^`;
- различие между отсутствующим и пустым `event_filter`;
- регистр обычных подклассов;
- специальные варианты сопоставления подклассов ядра, если они использовались;
- формат JSON;
- существующее построение routing key;
- независимость producer-профилей;
- поведение при повторных параметрах.

Строгий отказ на неизвестном событии и устранение дублей изменят наблюдаемое
поведение; эти изменения следует явно документировать. Для новых условий
целесообразно определить отдельную грамматику, сохранив понятное правило
совместного применения с прежним `event_filter`.

### 6.11. Проверки будущей реализации

Проверять нужно прежде всего:

1. Пересечения `ALL`, конкретного типа и подкласса: одна публикация на профиль.
2. Несколько профилей с разными правилами и совпадающими событиями.
3. Неизвестные имена, пустой фильтр, отсутствующий фильтр и повторные параметры.
4. Отсутствующие, пустые, многозначные и повторяющиеся заголовки; регистр имён
   и значений.
5. Ошибку создания после первого binding и полное снятие частичных подписок.
6. Повторные и параллельные reload под потоком событий.
7. Отсутствие изменения JSON и routing key при добавлении условий отбора.
8. Поведение очереди при недоступном брокере и остановке.

В просмотренных файлах тестов отдельного покрытия `mod_amqp` не обнаружено.
Существующие проверки событий находятся, в частности, в
[`tests/unit/switch_event.c`](../../../../tests/unit/switch_event.c).
