# Техническая проверка архитектуры Filter Engine для mod_amqp

Дата проверки: 26 октября 2026 года. Репозиторий: текущая рабочая копия
FreeSWITCH, HEAD `1ff547f988186de7f1903eba16d5477cde72e27d`.

Метод: статический анализ реализации модуля, event bindings, event headers,
hash-таблиц и очередей. Нагрузочные сценарии, fault injection, sanitizers и
проверки с RabbitMQ не запускались. Изменён только этот Markdown-отчёт.
Все ссылки на исходники относительны каталогу `docs/mod_amqp`; номера строк
соответствуют проанализированной версии.

## Вывод

Архитектура реализуема внутри `mod_amqp`, без изменения event API ядра.
Индивидуальный `switch_event_unbind()` обеспечивает необходимый барьер перед
освобождением профиля, если узлы принадлежат единственному владельцу и снятие
происходит вне event callback. Чтение заголовков без дополнительных аллокаций
возможно. Индекс по `event_id` подходит для выбора правил.

До реализации необходимо разрешить противоречие требований: точное сохранение
поведения `legacy` сохраняет существующие повторные вызовы при пересекающихся
подписках; глобальная гарантия «не более одного раза на профиль» их запрещает.
Рекомендуется гарантировать один проход в `rules`, а `legacy` оставить
совместимым. Если гарантия должна распространяться на оба режима, это должно
быть явно принято как изменение совместимости.

Критические изменения lifecycle: единое владение bindings, разделение
подготовки и активации профиля, безопасная очистка частичного создания и
сериализация управляющих операций. Удаление глобального unbind без переноса
этой ответственности в destructor небезопасно.

## 1. Проверка архитектурных требований

В отчёте используются три статуса:

- **Подтверждено исходниками** — механизм существует и применим при указанных
  условиях.
- **Требует изменения** — предлагаемая возможность отсутствует либо текущий
  lifecycle недостаточен.
- **Обнаружено ограничение** — требуется уточнение контракта, ограничение
  области гарантии или устранение конкретного риска.

### 1.1. Контракт режимов

**Статус: требует изменения.**

Рекомендуемый контракт:

- Нет параметра режима: `legacy`.
- `legacy`: действует существующий `event_filter`; новые rules не должны
  незаметно сужать или расширять его. Наличие неиспользуемой секции rules
  допустимо диагностировать предупреждением.
- `rules`: действует только whitelist rules. `event_filter` не участвует ни
  в выборе bindings, ни в runtime-фильтрации; его наличие также стоит
  диагностировать.
- Ноль правил в `rules`: deny all и ноль bindings.
- Ошибочное правило: отказ подготовки нового профиля/набора, с сохранением
  старого рабочего набора до начала переключения.
- Пустое правило без условий рекомендуется считать ошибкой. Иначе пустая
  конъюнкция математически равна true и превращает whitelist в allow all.
  Разрешение всех событий должно быть явным.

Основание: defaults и разбор сейчас общие для всех producer-профилей —
[`mod_amqp_producer_create()`, mod_amqp_producer.c:184](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L184).
Новой грамматики конфигурации в репозитории пока нет; в этом отчёте она не
представляется как существующий API.

### 1.2. Граница обещания «один раз»

**Статус: обнаружено ограничение.**

Примеры нынешних legacy-подписок, вызывающих дубли:

```text
ALL,CHANNEL_CREATE
CUSTOM,CUSTOM^sofia::register
CHANNEL_CREATE,CHANNEL_CREATE
```

Для подходящего события выполняется несколько callback и несколько постановок
в очередь. Это следует из регистрации каждого элемента в
[mod_amqp_producer.c:352](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L352)
и обхода узлов в
[switch_event.c:407](../../src/switch_event.c#L407).

Рекомендация: в `rules` гарантировать не более одного прохода callback и одного
сообщения на одну доставку события одному профилю. Совпадение нескольких правил
не должно порождать несколько сообщений. Совпадения в разных профилях
независимы. Повторная публикация после сетевой ошибки и повторное поступление
события — отдельные случаи; это не гарантия exactly-once доставки RabbitMQ.

Не добавлять отметки дедупликации в само событие: объект общий для подписчиков,
а `bind_user_data` ядро меняет перед каждым callback. Также не использовать
глобальный набор указателей событий: объекты освобождаются и адреса могут
переиспользоваться.

## 2. Event bindings и lifecycle

### 2.1. Индивидуальный unbind и параллельный callback

**Статус: подтверждено исходниками при единственном владельце узла.**

[`switch_event_deliver()`, switch_event.c:400](../../src/switch_event.c#L400)
держит `RWLOCK` на чтение в течение всего обхода подписок и выполнения callback.
[`switch_event_unbind()`, switch_event.c:2175](../../src/switch_event.c#L2175)
берёт тот же lock на запись, затем `BLOCK`, исключает узел из списка,
освобождает его и обнуляет переданный указатель.

Следствия:

1. Управляющий поток ждёт завершения уже выполняющейся доставки.
2. После снятия конкретного узла новые доставки через него невозможны.
3. Если у профиля несколько узлов, через остальные callback ещё возможен между
   отдельными вызовами unbind. Профиль и его правила должны жить до снятия
   последнего узла.
4. После возврата последнего успешного unbind нет callback этого профиля,
   удерживаемых этими подписками. Для синхронного matcher отдельный refcount
   не требуется, если профиль не используется где-либо ещё.
5. Lock глобальный: unbind может ждать и callback других модулей. Это барьер
   безопасности, а не гарантия ограниченной задержки остановки.

Рекомендация: снимать только ненулевые slots `event_nodes[]` из управляющего
потока; хранить профиль, очередь и правила до завершения всех unbind. Проверять
результат снятия ожидаемого зарегистрированного узла. `switch_event_unbind()`
не является безопасным способом проверить, жив ли произвольный указатель.

### 2.2. Глобальный unbind и устаревшие указатели

**Статус: требует изменения; обнаружен риск use-after-free.**

Глобальный
[`switch_event_unbind_callback()`, switch_event.c:2134](../../src/switch_event.c#L2134)
освобождает все узлы данного callback, но не знает об адресах slots
`profile->event_nodes[]` и не обнуляет их. Индивидуальный unbind затем использует
`n->event_id` из сохранённого узла: [switch_event.c:2189](../../src/switch_event.c#L2189).
Вызов по такому slot после глобального unbind — обращение к освобождённой
памяти, даже если функция в дальнейшем ищет узел по указателю.

Сейчас глобальные вызовы находятся в:

- [`mod_amqp_do_config()`, mod_amqp_utils.c:106](../../src/mod/event_handlers/mod_amqp/mod_amqp_utils.c#L106);
- [`mod_amqp_shutdown()`, mod_amqp.c:95](../../src/mod/event_handlers/mod_amqp/mod_amqp.c#L95).

Рекомендация: сделать destructor единственным владельцем удаления bindings
каждого producer-профиля и убрать оба глобальных вызова из нормального пути.
Это относится и к `legacy`, и к `rules`, если они используют тот же callback.
Не оставлять параллельный «страховочный» глобальный unbind.

Альтернатива с сохранением глобального снятия потребовала бы под общей
сериализацией обнулить все slots всех затронутых профилей и отдельно обработать
частично созданные профили. Она сложнее и для минимальной реализации не нужна.

### 2.3. Частичное создание и идемпотентная очистка

**Статус: требует изменения; обнаружен существующий риск use-after-free.**

Сейчас `mod_amqp_producer_create()` запускает поток, регистрирует bindings,
вставляет профиль в hash; любая последующая ошибка вызывает destructor через
`err:`. См.
[mod_amqp_producer.c:338](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L338)
и [mod_amqp_producer.c:374](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L374).
[`mod_amqp_producer_destroy()`, mod_amqp_producer.c:115](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L115)
сейчас bindings не снимает. При частичной регистрации они сохраняют
`user_data = profile` после уничтожения pool.

`switch_event_bind_removable()` обнуляет выходной slot при входе и записывает
его после успешной установки узла:
[switch_event.c:2069](../../src/switch_event.c#L2069),
[switch_event.c:2116](../../src/switch_event.c#L2116).
Pool allocation также обнуляет память:
[`switch_core_perform_alloc()`, switch_core_memory.c:518](../../src/switch_core_memory.c#L518).

Рекомендуемый порядок очистки из любой стадии создания:

```text
снять все реально зарегистрированные bindings
→ остановить sender с корректной синхронизацией флага
→ успешно join sender, если он создан
→ закрыть соединения и уничтожить оставшиеся сообщения
→ удалить только принадлежащую этому профилю запись hash
→ освободить compiled resources и pool
```

Пока снимаются bindings, profile остаётся полностью пригодным для callback.
Сначала снимать bindings, затем менять callback-visible состояние — проще,
чем пытаться защититься одним `running = 0`. Сам флаг не продлевает жизнь
объекта и не заменяет unbind.

Хранить состояние успешного создания потока и регистрации профиля отдельно
от запрошенного количества subscriptions. Не освобождать pool при неуспешном
join, если worker ещё может его использовать. Ресурсы с внешним allocator,
например compiled pattern при его наличии, освобождать явно: уничтожение
FreeSWITCH pool само по себе не является доказательством их освобождения.

### 2.4. Hash и подготовленный профиль с тем же именем

**Статус: требует изменения.**

Destructor безусловно вызывает `switch_core_hash_delete()` по имени:
[mod_amqp_producer.c:129](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L129).
Если подготовить новый профиль с именем работающего и затем отклонить его,
такой destructor удалит из hash старый профиль.

Кроме того, `switch_core_hash_insert()` не запрещает дубликат имени:
[switch_core.h:1479](../../src/include/switch_core.h#L1479),
[`switch_core_hash_insert_destructor()`, switch_core_hash.c:144](../../src/switch_core_hash.c#L144),
[`switch_hashtable_insert_destructor()`, switch_hashtable.c:194](../../src/switch_hashtable.c#L194).
Существующая запись заменяется без автоматического уничтожения producer.

Рекомендация: staging не публиковать в активный hash. Под общей сериализацией
удалять запись только если профиль действительно зарегистрирован и
`switch_core_hash_find(hash, name)` возвращает именно его. Дубликаты имён
в новом наборе отклонять до переключения. У старого и нового экземпляров
одного логического профиля не должно быть одновременно активных bindings.

### 2.5. Deadlock и порядок блокировок

**Статус: обнаружено ограничение.**

Нельзя выполнять bind/unbind/reload синхронно из event callback: callback уже
удерживает read lock `RWLOCK`, а bind/unbind требуют write lock. API не содержит
механизма безопасного upgrade. Тот же риск есть при косвенном вызове reload
через API из callback.

Нельзя строить следующий цикл:

```text
callback: держит read(RWLOCK), ждёт mutex конфигурации
reload:   держит mutex конфигурации, ждёт write(RWLOCK) в unbind
```

Рекомендация: один mutex для управляющих операций load/reload/shutdown;
callback читает неизменяемые правила без этого mutex. Sender также не должен
захватывать управляющий mutex, если управляющий поток держит его во время join.
Не держать mutex, нужный callback или sender, при unbind/join.

Дополнительный существующий путь: AMQP command worker синхронно вызывает
`switch_console_execute()`:
[mod_amqp_command.c:476](../../src/mod/event_handlers/mod_amqp/mod_amqp_command.c#L476).
Команда `amqp` вызывает полный reload, который уничтожает command profiles;
[`mod_amqp_command_destroy()`, mod_amqp_command.c:59](../../src/mod/event_handlers/mod_amqp/mod_amqp_command.c#L59)
делает join соответствующего command worker. Reload, запущенный таким worker,
может попытаться join самого себя; обработка ошибки join не обеспечивает
сохранение используемого им профиля. Это риск self-join/освобождения живого
профиля, а не доказательство одинакового поведения на всех pthread-платформах.
Если сохраняется полный reload, его выполнение нужно перенести в независимый
управляющий контекст либо явно отклонять такой источник запроса до teardown.

### 2.6. Состояние callback и worker

**Статус: обнаружено ограничение; требует синхронизации.**

`running` — обычный `switch_bool_t`; его читает sender и меняет destructor.
`circuit_breaker_reset_time` читается и записывается параллельными callback:
[mod_amqp.h:128](../../src/mod/event_handlers/mod_amqp/mod_amqp.h#L128),
[mod_amqp_producer.c:84](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L84),
[mod_amqp_producer.c:134](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L134),
[mod_amqp_producer.c:450](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L450).

Индивидуальный unbind решает lifetime callback, но не гонку stop-флага с sender
и не гонку breaker между callback. Для stop-флага доступны реальные
`switch_atomic_read()` / `switch_atomic_set()`:
[switch_apr.c:1395](../../src/switch_apr.c#L1395). Timestamp breaker требует
подходящего механизма синхронизации своей разрядности либо короткого mutex;
нельзя считать 32-битный atomic универсальной заменой `switch_time_t`.

## 3. Event Index и subscriptions

### 3.1. Границы массива

**Статус: подтверждено исходниками; обнаружена ошибка при включительной границе.**

`switch_event_types_t` — последовательный enum от `SWITCH_EVENT_CUSTOM = 0`
до `SWITCH_EVENT_ALL` включительно:
[switch_types.h:2082](../../src/include/switch_types.h#L2082).
В ядре таблица объявлена как `EVENT_NODES[SWITCH_EVENT_ALL + 1]`:
[switch_event.c:87](../../src/switch_event.c#L87).
`switch_name_event()` перебирает значения с условием `<= SWITCH_EVENT_ALL`:
[switch_event.c:444](../../src/switch_event.c#L444).

Массив `[SWITCH_EVENT_ALL]` корректен только для индексов
`0 <= id < SWITCH_EVENT_ALL`. Индекс `ALL` в нём находится за границей.
Нынешние `events[]` и `event_nodes[]` модуля — списки подписок, индексируемые
порядковым номером, а не готовый Event Index.

Рекомендация: для новой таблицы, включающей slot `ALL`, использовать размер
`SWITCH_EVENT_ALL + 1`. Для итераций явно различать конкретные типы (`< ALL`)
и весь диапазон со служебным slot (`<= ALL`). Число правил не ограничивать
значением `SWITCH_EVENT_ALL`; в каждом bucket может быть много правил.

### 3.2. Прямая индексация evt->event_id

**Статус: подтверждено исходниками при проверенном диапазоне.**

Ядро само индексирует `EVENT_NODES` через `event_id` в
[`switch_event_deliver()`](../../src/switch_event.c#L407).
Это позволяет аналогичную O(1) выборку bucket в engine. Перед собственной
индексацией проверять, что значение лежит в поддерживаемом диапазоне; не
рассчитывать, что тип enum автоматически проверяет данные.

`ALL` — прежде всего wildcard подписки, однако нельзя доказывать его
невозможность в `evt->event_id` только его названием:
[`switch_event_create_subclass_detailed()`](../../src/switch_event.c#L747)
не отклоняет `ALL` без subclass, а доставка при `event_id == ALL` обходит
этот список один раз. Рекомендуется иметь определённый безопасный путь и
тест для этого значения, а не читать за границей массива. Защита engine не
исправляет невалидную индексацию, которая могла произойти в ядре до callback.

### 3.3. Организация индекса

**Статус: требует изменения.**

Для минимальной реализации подходит таблица buckets размера `ALL + 1`:

- В конкретном bucket хранятся ссылки на правила с соответствующим точным
  Event-Name.
- Slot `ALL` содержит общие правила: явный wildcard либо отсутствие ограничения
  Event-Name.
- Для обычного события проверяются конкретный bucket и общий bucket; между
  ними OR. После первого полного совпадения — true.
- При `evt->event_id == ALL` общий bucket проверяется один раз.
- Одно правило не помещается одновременно в общий и конкретный bucket для
  одного и того же пути выполнения; списки имён нормализуются без повторов.

Это сохраняет O(1) доступ к спискам и не требует копировать каждое wildcard-
правило во все buckets. Общие правила неизбежно проверяются для всех типов.
Альтернатива — развернуть wildcard в каждый конкретный bucket при компиляции;
она уменьшает число списков на callback, но увеличивает память до O(R × E).
Для первого варианта достаточно хранения ссылок на неизменяемые правила.

Для точного Event-Name компиляция использует `switch_name_event()`, но в новом
режиме нужна строгая проверка входной формы: текущая функция сравнивает суффикс
после 13 символов без проверки самого префикса. Не переносить эту случайную
особенность в новую грамматику; `legacy` при этом остаётся прежним.

Если появятся regex или другие неточные операции по Event-Name, нельзя
неверно вычислять узкий набор кандидатов. Либо развернуть их по каноническим
именам enum при компиляции, либо поместить в общий bucket и подписаться на
`ALL`. Набор subscriptions должен быть надмножеством событий, которые могут
пройти правила.

### 3.4. Уникальные subscriptions и ALL

**Статус: требует изменения; механизм ядра подтверждён.**

Для `rules`:

1. Собрать множество конкретных типов из скомпилированного индекса.
2. Если есть общие правила, зарегистрировать только один `ALL` binding.
3. Иначе зарегистрировать по одному binding на конкретный тип.
4. Всегда передавать `subclass = SWITCH_EVENT_SUBCLASS_ANY`, то есть `NULL`.
5. Проверять subclass и остальные условия внутри matcher.
6. При пустом whitelist не создавать bindings.

Основание: core matching
[`switch_events_match()`](../../src/switch_event.c#L233)
и регистрация
[`switch_event_bind_removable()`](../../src/switch_event.c#L2060).
Bindings по нескольким подклассам одного типа вместе с binding этого типа
создадут пересечения; push-down таких условий в первой реализации не нужен.

Наличие `ALL` в subscriptions не означает автоматического разрешения события:
callback всё равно должен пройти whitelist. Нельзя одновременно оставлять
`ALL` и конкретные bindings одного rules-профиля. Нельзя использовать текущую
дефолтную legacy-подписку как неявный дополнительный binding.

## 4. Event Headers

### 4.1. Реальный getter и отсутствие аллокаций

**Статус: подтверждено исходниками; обнаружены особенности lookup.**

`switch_event_get_header()` — macro для вызова
`switch_event_get_header_idx(event, name, -1)`:
[switch_event.h:170](../../src/include/switch_event.h#L170).

`switch_event_get_header_ptr()` вычисляет case-insensitive hash имени и
линейно обходит `event->headers`, возвращая первый подходящий узел; имя
дополнительно сравнивается через `strcasecmp()`:
[switch_event.c:825](../../src/switch_event.c#L825).
Это не O(1) hash lookup.

`switch_event_get_header_idx()` возвращает:

- при `idx == -1` — `hp->value`;
- при допустимом неотрицательном индексе массива — `hp->array[idx]`;
- при отсутствии настоящего заголовка с именем `_body` — `event->body`;
- в остальных случаях — `NULL`.

См. [switch_event.c:846](../../src/switch_event.c#L846).
На scalar-заголовке `get_header_idx(..., 0)` не заменяет обычный getter:
при `hp->idx == 0` он вернёт `NULL`.

Lookup не выделяет память. Возвращается заимствованный указатель: его нельзя
освобождать, изменять или сохранять после callback. Для engine использовать
`const`-доступ, не создавать JSON/копию события ради сравнения.

Рекомендация: различать отсутствие и пустое значение; не использовать
`switch_event_get_header_nil()`, стирающий это различие. Решить отдельно,
поддерживается ли `_body` как специальное поле: `get_header_ptr()` и строковый
getter имеют для него различное поведение при отсутствии узла.

### 4.2. Массивы и повторяющиеся узлы — разные представления

**Статус: подтверждено исходниками; семантика matcher требует определения.**

[`switch_event_header_t`, switch_event.h:65](../../src/include/switch_event.h#L65)
содержит `value`, `array`, `idx` и `next`.

| Представление | Реализация | Последствие для фильтра |
| --- | --- | --- |
| Scalar | `idx == 0`, значение в `value` | Сравнивать scalar напрямую |
| Массив в одном узле | `SWITCH_STACK_PUSH`, `SWITCH_STACK_UNSHIFT` или индексированная запись; [switch_event.c:1029](../../src/switch_event.c#L1029), [switch_event.c:1109](../../src/switch_event.c#L1109) | Значения в `array[0..idx-1]`; `value` — уже построенное текстовое представление, при нескольких значениях вида `ARRAY::a\|:b` |
| Несколько одноимённых узлов | Обычное добавление может создать новый узел, если нет `EF_UNIQ_HEADERS`; [switch_event.c:1087](../../src/switch_event.c#L1087), [switch_event.c:1183](../../src/switch_event.c#L1183) | Обычный getter видит только первый подходящий узел; следующие не исчезают |

`EF_UNIQ_HEADERS` автоматически выставляется лишь для некоторых типов,
в частности `REQUEST_PARAMS`, `CHANNEL_DATA`, `MESSAGE`:
[switch_event.c:772](../../src/switch_event.c#L772).
Нельзя считать все события набором уникальных scalar-заголовков.

Рекомендация для положительного условия равенства: ANY по логическим значениям
всех одноимённых узлов, а внутри массива — по его элементам. Не сравнивать
ожидаемое значение только с `ARRAY::…` и не парсить эту строку заново.
Обход `hp->next` с case-insensitive сравнением имён и чтение `array` не требуют
аллокаций. В существующем API нет отдельного iterator «следующее одноимённое
поле»; обход нужно реализовать локально.

При двух AND-условиях на одно имя каждое ANY-условие может удовлетвориться
разным значением. Это следует явно закрепить тестом. Отрицание и deny rules
не нужны для предложенного whitelist; если отрицательные операторы когда-либо
появятся, их кванторы нельзя выводить из положительного ANY автоматически.

### 4.3. Event-Name и Event-Subclass как канонические поля

**Статус: обнаружено ограничение; рекомендуется явный контракт.**

Внутренние поля и одноимённые заголовки — разные данные. Создание обычно
синхронизирует их:
[`switch_event_prep_for_delivery_detailed()`, switch_event.c:1985](../../src/switch_event.c#L1985),
[`switch_event_create_subclass_detailed()`, switch_event.c:781](../../src/switch_event.c#L781),
[`switch_event_set_subclass_name()`, switch_event.c:1227](../../src/switch_event.c#L1227).
Но запись произвольного заголовка не доказывает соответствующее изменение
внутреннего поля.

Рекомендуется в `rules` трактовать Event-Name как `evt->event_id`, а
Event-Subclass как `evt->subclass_name`. Это согласуется с Event Index и
нынешними native bindings. Имена заголовков — без учёта регистра; точные
значения обычных заголовков и subclass — с учётом регистра, если иное явно
не задано контрактом.

Если требуется именно буквальное сравнение заголовка `Event-Name`, отличного
от внутреннего ID, нельзя сужать subscriptions только по значению этого
заголовка: событие может иметь другой `event_id` и не попасть в callback.
Тогда нужен консервативный общий bucket/`ALL` и runtime-проверка. Не разрешать
две неявные противоречащие трактовки одного selector.

### 4.4. Потокобезопасность чтения

**Статус: подтверждено для синхронного чтения; обнаружено ограничение общего доступа.**

Для одного вызова `switch_event_deliver()` callbacks идут последовательно,
а объект уничтожается после них:
[switch_event.c:400](../../src/switch_event.c#L400).
Разные события исполняются параллельно через dispatch threads либо thread pool:
[switch_event.c:272](../../src/switch_event.c#L272),
[switch_event.c:299](../../src/switch_event.c#L299),
[switch_event.c:2026](../../src/switch_event.c#L2026).

Getter не берёт event mutex; `RWLOCK` защищает bindings, а не является
универсальной блокировкой записи заголовков. Безопасный engine читает событие
синхронно, не изменяет его, не передаёт указатели на headers в sender и не
пишет per-event результаты в общий compiled rule. Внешняя одновременная
модификация того же объекта за пределами этого контракта getter не защищена.
Предыдущий callback может изменить событие последовательно — matcher увидит
состояние на момент своего вызова, а не гарантированный исходный snapshot.

Рекомендация: immutable rules и только локальное состояние вычисления.
Неизменяемость compiled pattern сама по себе не доказывает thread-safety
библиотеки исполнения: если будут regex, её scratch/match state должен быть
локальным для вызова или потока, а не общим изменяемым полем правила.

## 5. Предварительная компиляция и reload

### 5.1. Подготовка без побочных эффектов

**Статус: возможна; требует разделения текущего create.**

[`mod_amqp_do_config()`](../../src/mod/event_handlers/mod_amqp/mod_amqp_utils.c#L90)
сначала открывает XML, но затем уничтожает старые профили и только после этого
вызывает `mod_amqp_producer_create()`. Сам create запускает поток, bindings
и hash insertion. Поэтому его нельзя использовать как операцию staging.

Рекомендация: логически разделить подготовку и активацию, без требования новых
публичных API ядра. Подготовка должна:

1. Разобрать режимы, параметры и правила во временный набор профилей.
2. Проверить имена, операторы, лимиты, дубликаты profile names и типы событий.
3. Скопировать все используемые строки из XML в принадлежащий профилю pool.
4. Подготовить сравнения/паттерны, Event Index и subscriptions.
5. Не создавать event bindings, не запускать sender и не менять активный hash.
6. При любой ошибке освободить только подготовленные объекты.

XML освобождается в конце `mod_amqp_do_config()`:
[mod_amqp_utils.c:196](../../src/mod/event_handlers/mod_amqp/mod_amqp_utils.c#L196).
Сохранять pointers на XML attributes в compiled rules после этого нельзя.

### 5.2. Последовательная замена

**Статус: безопасна при описанном порядке; не является бесшовной транзакцией.**

Минимальный вариант:

```text
сериализовать управляющую операцию
→ подготовить и проверить весь новый producer-набор
→ при ошибке оставить старый набор без изменений
→ снять все bindings старого набора
→ остановить/join и освободить старые профили
→ активировать новый набор, регистрируя только полностью готовые профили
→ опубликовать активные профили в hash с корректным учётом владения
```

При регистрации первого binding новый профиль уже должен иметь готовые
immutable rules, очередь и безопасно запущенный sender. Callback может
выполниться до завершения регистрации всех его bindings и до вставки в hash:
[mod_amqp_producer.c:352](../../src/mod/event_handlers/mod_amqp/mod_amqp_producer.c#L352).
Это допустимо при полной готовности profile, но исключает ленивую достройку
индекса после bind.

Безопасность lifetime не означает отсутствие потерь: между наборами есть
окно без подписок, остатки старых очередей нынешний destructor уничтожает.
События, поставленные в core event queue до reload, могут получить новую
фильтрацию, если доставлены уже после переключения: bindings выбираются
в момент `switch_event_deliver()`, не при создании события.

Активация может отказать после успешной компиляции: создание потока, очереди
или bindings остаётся отдельным этапом. При отказе нужно снять все частичные
bindings нового набора и вернуть ошибку. Если старый набор уже уничтожен,
откат не гарантирован. Для минимальной версии документировать это; для
гарантированного rollback нужна отдельная схема сохранения/реактивации старых
ресурсов. «Предварительная компиляция» сама по себе не даёт rollback активации.

Не активировать новый профиль до снятия bindings старого профиля с тем же
именем: иначе одно событие может пройти оба поколения. При последовательном
удалении старых и добавлении новых bindings read/write lock ядра исключает
изменение списков посреди одной выполняющейся доставки.

**Статус: обнаружено ограничение.**

[mod_amqp_utils.c:196](../../src/mod/event_handlers/mod_amqp/mod_amqp_utils.c#L196).
Новый код должен возвращать достоверный результат и явно определять, относится

При reload logging callback снимается и в этом пути не регистрируется снова:
[mod_amqp_utils.c:117](../../src/mod/event_handlers/mod_amqp/mod_amqp_utils.c#L117);
первичная регистрация находится в
[mod_amqp.c:78](../../src/mod/event_handlers/mod_amqp/mod_amqp.c#L78).
Это существующий дефект соседнего lifecycle. Его нельзя принимать за штатное
свойство Filter Engine; если общий reload остаётся, включить в regression tests.

API `amqp` не вызывает `switch_xml_reload()` и не подписан на `RELOADXML`.
Источник XML остаётся существующим
[`switch_xml_open_cfg()`, switch_xml.c:2499](../../src/switch_xml.c#L2499).
Компилятор rules должен работать с полученным snapshot; не обещать, что вызов
`amqp` сам перечитает файловую XML-конфигурацию ядра.

## 6. Минимальный план реализации

1. **Зафиксировать контракт.** Один проход гарантировать в `rules`; для
   `legacy` оставить совместимое поведение либо отдельно согласовать изменение
   дублей. Определить canonical Event-Name/Subclass, ANY для многозначных
   headers, пустые правила, ошибки и пределы числа правил/условий.
2. **Исправить владение и teardown.** Перевести producer bindings на единый
   индивидуальный unbind; убрать глобальные producer-unbind из reload/shutdown.
   Обработать частичную активацию, владение hash и результаты join.
3. **Разделить подготовку/активацию.** Новый набор готовится без потоков,
   bindings и изменения active hash. Проверить имена и скопировать XML-строки.
   Общий mutex используется только управляющим контекстом.
4. **Добавить compiler и Event Index.** Immutable правила и ссылки в buckets
   `[SWITCH_EVENT_ALL + 1]`; общий slot `ALL`; уникальные subscriptions.
   Нулевой whitelist не создаёт подписок. Неизвестное событие в `rules`
   отклоняется, не наследует default `ALL`.
5. **Добавить matcher.** OR/AND с short-circuit, чтение borrowed headers и
   массивов без копирования, одно решение до выделения сообщения и JSON.
   Неизменность compiled data при параллельных вызовах обязательна.
6. **Включить в reload.** Сначала подготовка всего producer-набора, затем
   последовательный cutover без перекрытия поколений. Чётко обработать ошибку
   активации и документировать окно потерь. Исключить выполнение teardown
   в callback или уничтожаемом command worker.
7. **Проверить совместимость и конкуренцию.** Синхронизировать stop/breaker;
   выполнить тесты ниже до изменения рекомендуемого режима по умолчанию.

[`tests/unit/README:4`](../../tests/unit/README#L4). Проверки доставки и
конкурентного teardown должны использовать реальное ядро событий; одних
mock-проверок matcher недостаточно.

| Группа | Сценарии и ожидаемый результат |
| --- | --- |
| Режимы | Отсутствующий режим равен `legacy`; явные режимы независимы; неизвестный режим отвергается до teardown. В `rules` `event_filter` не влияет на результат |
| Legacy compatibility | Сравнить старую и новую реализации на отсутствии/пустом `event_filter`, коротких/префиксных именах, `^subclass`, регистре, повторных параметрах и ошибочном имени. Кратность пересечений соответствует принятому решению по совместимости |
| Whitelist | Ноль правил — ноль сообщений и bindings. Нет совпадения — отказ. Одно совпадение — разрешение. Пустое правило отклоняется, явный ALL разрешает только при выполнении остальных условий |
| OR/AND | Один ложный предикат делает правило ложным; другое подходящее правило разрешает событие. Несколько совпавших правил дают одну сериализацию и один enqueue |
| Event Index | `CUSTOM = 0`, последний конкретный enum, `ALL`; неверные значения в прямом вызове matcher безопасно отклоняются. Один и тот же ID в selector не дублирует правило/подписку |
| Wildcard | Общие и конкретные правила проверяются корректно. При наличии общих правил зарегистрирован только `ALL`; `evt->event_id == ALL` не проверяет общий список дважды |
| Subclass | Одинаковый event ID и разные subclasses; отсутствие subclass; точный регистр; отсутствие неявной поддержки `*`, `file:`/`func:` в rules, если она не предусмотрена новым контрактом |
| Canonical fields | Преднамеренно различающиеся `event_id` и header `Event-Name`, `subclass_name` и header `Event-Subclass`: matcher следует выбранному контракту, индекс не пропускает допустимых кандидатов |
| Header lookup | Разный регистр имени, отсутствующее имя, scalar, пустое значение, `_body` с узлом и без узла, если поле поддерживается. Scalar не читается как array index 0 |
| Arrays | PUSH, UNSHIFT, индексированная запись, несколько значений; ANY сравнивает элементы, а не текст `ARRAY::…`. Пустые значения проверять через допускающее их реальное представление, учитывая удаление пустого scalar стандартным add-header |
| Duplicate headers | Несколько одноимённых узлов, включая сочетание scalar и array: проверяются все логические значения. Два AND-условия на одном имени могут совпасть на разных элементах согласно контракту |
| Нет изменений события | После matcher идентичны headers, body и subclass; порядок callback не повреждён. Отброшенное событие не вызывает JSON serializer и не создаёт AMQP message |
| Горячий путь | Инструментировать аллокации при scalar/array equality: lookup/matcher не выделяет память. Отдельно проверить regex execution, если он будет добавлен |
| Персональный unbind | Два профиля: удаление одного не снимает другой. Удаляемый профиль имеет несколько bindings; все slots обнуляются, повторная очистка безопасна |
| Callback против unbind | Удержать callback барьером, запустить destroy с другого потока: pool не освобождается до выхода callback. События, доставляемые после снятия узлов, не вызывают удалённый профиль |
| Частичная активация | Fault injection после 0/1/N bindings, после запуска потока и при hash insertion: нет оставшихся узлов, живого sender на освобождённом pool и утечек compiled resources |
| Staging и имена | Ошибка подготовленного профиля с именем рабочего не удаляет active hash entry. Дубликаты имён нового набора отклоняются; очистка старого поколения не удаляет новое |
| Ошибка компиляции при reload | Рабочие profiles/bindings и очереди сохраняются, ошибка возвращается вызывающему коду. Ни один новый binding не появился |
| Успешный reload | Под потоком событий нет одновременных bindings двух поколений одного имени. Допустимые потери в окне переключения измерены; события из core queue используют правила поколения на момент доставки |
| Ошибка активации | После успешной компиляции отказ очереди/потока/bind обрабатывается по документированной политике; новый частичный набор полностью снят, фиктивного success нет |
| Конкурентное управление | Два reload, reload/shutdown и reload во время частичной активации сериализованы; нет double-unbind, устаревших узлов и порчи hash |
| Контекст управления | Запрос из callback и AMQP command worker отклонён или перенесён в безопасный контекст до teardown; нет read-to-write upgrade, self-join и ожидания mutex worker во время join |
| Соседние профили | Producer lifecycle не ломает command/logging; если reload остаётся общим, logger возобновляет доставку после reload |
| Гонки и lifetime | ASan/UBSan на teardown/границах, TSan на параллельных callback, stop и breaker. При наличии regex нет общего изменяемого match state |
| Производительность | Много правил одного типа, много общих правил, длинный список headers, частые reload: измерить стоимость matcher и задержку unbind под нагрузкой |
