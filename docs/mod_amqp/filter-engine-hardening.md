## Что изменено

- [mod_amqp.c](../../src/mod/event_handlers/mod_amqp/mod_amqp.c#L47), [mod_amqp.h](../../src/mod/event_handlers/mod_amqp/mod_amqp.h#L213): синхронизированное состояние ACTIVE, DEGRADED, RESTART_REQUIRED с константной диагностикой без credentials. Команда api amqp status выдаёт состояние и restart_required; api amqp без аргумента по-прежнему выполняет конфигурационный reload и возвращает прежние +OK/-ERR. Получение status не ждёт lifecycle mutex.
- [mod_amqp_load()](../../src/mod/event_handlers/mod_amqp/mod_amqp.c#L100): успешная первичная активация возвращает SWITCH_STATUS_NOUNLOAD. Core [load_file](../../src/switch_loadable_module.c#L1720) устанавливает permanent до публикации интерфейсов. Повторный прямой вызов load проверяет сохранённый pool до memset. Обычный и forced unload в [Core](../../src/switch_loadable_module.c#L1889) отклоняются до удаления registry/interfaces и до shutdown; Core reload mod_amqp поэтому также отклоняется. Изменение бинарника требует перезапуска процесса FreeSWITCH, а не module reload.
- При ошибке initial load с полной успешной очисткой load возвращает GENERR, и последующая загрузка возможна. При retained resource load возвращает NOUNLOAD, сохраняет DSO/pool и API status показывает RESTART_REQUIRED; api amqp отвергается. Это ограничение Core: module_exists может быть успешным при неработоспособном модуле. Поэтому мониторинг должен читать api amqp status, а не только module_exists.
- [mod_amqp_do_config()](../../src/mod/event_handlers/mod_amqp/mod_amqp_utils.c#L175): ошибка подготовки до teardown сохраняет прежнее состояние и набор, меняет только диагностический detail. Ошибка после начала переключения помечает DEGRADED; повторный config reload разрешён и успешный переход возвращает ACTIVE. Для RESTART_REQUIRED после initial retained shutdown-флаг запрещает config reload, status доступен. Подготовка набора до teardown, удаление старых bindings до новых, retained owners, транспорт, rules/legacy, JSON и routing не изменены.
- [Makefile.am](../../src/mod/event_handlers/mod_amqp/Makefile.am#L13): явные зависимости объектов модуля от mod_amqp.h и тестовых translation units от включённых production исходников/helpers. Проверка выявила реальную опасность: dummy .Plo оставил старый producer object после изменения layout globals; первый loader probe упал в switch_hashtable_search. После добавления prerequisite все production objects пересобраны, probe проходит. [Проверка зависимостей](hardening-artifacts/check-deps.sh) доказала шесть recompiles/relinks и стабильный no-op, сохранив SHA исходников и mtime.
- Сохранены исправления предыдущих шагов: синхронизация command/logging running и thread identity в [command](../../src/mod/event_handlers/mod_amqp/mod_amqp_command.c), [logging](../../src/mod/event_handlers/mod_amqp/mod_amqp_logging.c), [utils](../../src/mod/event_handlers/mod_amqp/mod_amqp_utils.c); worker-loop cases и исправление sanitizer proxy build. Новые [ESL-кейсы](../../src/mod/event_handlers/mod_amqp/test/api_reply_cases.h) проверяют ACTIVE после ошибки подготовки, DEGRADED с восстановлением, RESTART_REQUIRED с запретом config reload.

## Изолированные loader-процессы

[Harness](acceptance-artifacts/loader-fault-main.c) и [interposer](acceptance-artifacts/loader-fault-interposer.c) запускаются с отдельным Core и fault injection; exit 0 означает выполнение проверяемого контракта. Все три запуска завершились с кодом 0:

| Сценарий | Наблюдение |
| --- | --- |
| [normal](hardening-artifacts/loader-normal-v3.log) | load=0, unload=16, force=16, repeat load=1; registry, API, DSO и два bindings остались. Core reload вернул ошибки unload/load. Тестовое событие доставлено callback ровно один раз; status ACTIVE. Config reload дал +OK. |
| [initial-clean](hardening-artifacts/loader-initial-clean-v3.log) | первый load=9, registry/API отсутствуют; после снятия fault повторный load=0 и status ACTIVE. |
| [initial-retained](hardening-artifacts/loader-initial-retained-v3.log) | Core считает load успешным (0), status RESTART_REQUIRED; unload/force запрещены, duplicate load отклонён, два bindings сохранены, test callback доставлен, config reload дал -ERR. Три fault-injected unbind остались неуспешными. |

Проверки registry/API/bindings/DSO не равны полному доказательству состояния всех globals или workers: внутренний symbol mod_amqp_globals не экспортируется; worker-liveness в этих loader probes напрямую не измеряется. Отдельные integration worker cases проверяют join/retained owner с контролируемым I/O, но не весь Core shutdown и не реальные сетевые deadlines.

## Блокер завершения процесса

[Core switch_core_destroy()](../../src/switch_core.c#L3019) посылает SWITCH_EVENT_SHUTDOWN перед module teardown, затем вызывает switch_loadable_module_shutdown(), event shutdown и остановку pools. Однако [switch_event_fire_detailed()](../../src/switch_event.c#L2006) только ставит событие в очередь/dispatch pool и не ждёт его доставки. [Core module shutdown](../../src/switch_loadable_module.c#L2410) пропускает permanent-модули. [switch_event_deliver()](../../src/switch_event.c#L400) держит read RWLOCK во время callback, а [switch_event_unbind()](../../src/switch_event.c#L2175) берёт write RWLOCK: прямой teardown из shutdown callback создаёт read-to-write deadlock. Перенос teardown в отдельный поток не создаёт барьера перед уничтожением event engine и pools; для callback возможны гонки и use-after-free. SWITCH_EVENT_SHUTDOWN_REQUESTED ещё раньше, асинхронно и может не соответствовать фактическому завершению; atexit уже слишком поздно. Поддерживаемого синхронного pre-Core-teardown hook без изменения Core в этой версии не найдено.

Поэтому участок process shutdown сознательно **не реализован**. Не выполнен требуемый probe завершения отдельного Core-процесса с реальными workers и контролируемым I/O: проверять его до появления корректного механизма было бы ложной приёмкой. Обязательная зависимость для завершения варианта B — поддерживаемая синхронная точка shutdown до event/pool teardown либо пересмотр запрета на узкое изменение Core loader/lifecycle. Операционный pre-stop вне Core мог бы уменьшить риск штатного обслуживания, но не гарантирует безопасность всех путей завершения и не закрывает требование.

## Эксплуатационный контракт и следующие проверки

При штатной работе разрешён api amqp для config reload; после него нужно проверить api amqp status. ACTIVE означает успешную активацию, DEGRADED допускает исправленный config reload, RESTART_REQUIRED требует перезапуска процесса и запрещает reload. Обновление бинарника планируется как остановка/запуск FreeSWITCH целиком с проверкой status и возможностью отката прежнего бинарника; до закрытия process-shutdown блокера этот порядок нельзя считать доказанно безопасным. Команда reload mod_amqp, обычный и forced unload должны возвращать отказ.

Для снятия BLOCKED необходимы: (1) доказанный синхронный shutdown hook и отдельный Core-process probe с реальными producer/command/logging workers, контролируемым I/O и проверкой unbind→join→pool; (2) локализация integration ASan с воспроизводимым минимальным примером либо исправление обнаруженного lifetime defect и зелёный повторный прогон; (3) повторная аварийная loader/regression проверка после любого исправления. Надёжность доставки RabbitMQ в объём этого hardening не входит.
